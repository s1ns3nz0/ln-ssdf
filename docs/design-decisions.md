# 인터뷰 결정 — 2026-09-21

이 문서는 사용자가 grill-me 인터뷰에서 확정한 설계의 기준이다. 아래 항목은 **합의됨·기술 검증 대기** 상태이며 구현 완료를 뜻하지 않는다. 기존 HANDOFF 문서와 충돌하면 이 결정을 우선한다.

## Vault와 LN 운영

- 언실러는 영속 저장소를 사용하는 일반 Vault다. 최초 기동·복구 시 수동 unseal하고, 메인 Vault는 transit auto-unseal을 사용한다.
- kind 클러스터 삭제 후 호스트 백업으로 복원할 수 있어야 한다. 언실러 데이터 백업과 unseal 키는 Git 밖에서 분리 보관하고 메인 Vault Raft 스냅샷도 포함한다. 호스트 디스크 손실은 첫 데모의 복구 범위 밖이다.
- lnd의 DB 자격증명 교체는 짧은 계획 중단을 허용한다. 새 자격증명 반영, lnd 재시작, DB 재연결, 결제 성공을 검증한다. Secret 갱신만으로 성공 처리하지 않는다.
- 교체 순서는 새 계정 발급 → 권한 확인 → lnd 재시작 → DB 재연결·결제 성공 → 기존 계정 폐기다. 임대 만료 전에 전환을 시작하고, 실패 시 아직 유효한 기존 계정으로만 롤백한다.
- 같은 regtest bitcoind에 lnd 두 대를 연결한다. 주 노드는 Vault·Postgres, 상대 노드는 테스트용 bbolt를 사용한다. 채널 개설과 양방향 결제가 필수이며 다중 홉은 후순위다.
- 복구 드릴은 kind 재생성, Vault·DB 복원, lnd 기동, 증거 원장 검증을 포함한다. Lightning 채널 복구는 별도 검증하며 SCB 복구를 기존 채널의 정상 운영 재개와 동일시하지 않는다. 실제 복구 시간·데이터 손실 구간을 측정한 뒤 RTO·RPO 목표를 정한다.

## 화면과 판정

- 추가 대시보드는 **Manyfast MCP**로 만든다. 전역 MCP 등록·OAuth 인증과 프로젝트 기획서 업로드를 완료했다. Manyfast 프로젝트 ID는 `6cd5f81c-25ad-469d-9643-f105324f5e99`이며 화면과 실제 데이터 연동은 미구현이다.
- Grafana는 운영 지표·로그를 담당한다. 추가 화면은 요구사항별 상태, 근거 증거, 수집·만료 시각, 예외 사유를 탐색하는 읽기 전용 화면이다.
- 첫 버전은 로컬 접속이다. 브라우저는 정제된 증거를 반환하는 읽기 전용 API만 호출한다. Postgres·Vault·ArgoCD에 직접 접속하지 않으며 시크릿·토큰·원본 로그를 응답에 포함하지 않는다.
- 백엔드가 상태·TTL·예외를 판정한다. 배포 게이트·exporter·읽기 전용 API는 같은 판정 결과를 사용하고, 화면은 표시·집계만 한다.
- 요구사항을 세부 검사로 나누고 필수 검사가 모두 통과해야 `satisfied`다. 확인된 실패가 있으면 `not_satisfied`를 우선 표시하되 누락·만료도 숨기지 않는다.
- 필수 요구사항은 `satisfied`만 배포를 허용한다. `no_evidence`, `not_implemented`, `not_satisfied`는 차단한다. `not_applicable`은 Git에 사유·적용 범위가 기록된 경우만 제외한다. 참고용 요구사항은 표시하되 차단하지 않는다.
- 구체적인 DB 스키마는 아직 미확정이다. 기존 4테이블 예시는 대상·트랙별 평가, 복수 증거, 세부 검사, TTL, 정책 버전, 예외, 승인 연결을 표현하도록 수정해야 한다.

## OSCAL 기반 관리

- 요구사항·구현 설명·평가 결과의 관리 기준으로 OSCAL을 채택한다. 채택 결정과 실제 변환·연동 성공은 구분한다.
- Catalog는 204D 요구사항·원문 출처·평가 목적, Profile은 적용 요구사항과 조정값, Component Definition은 컴포넌트별 통제 구현 설명을 관리한다. 프로젝트가 작성한 204D Catalog를 NIST가 배포한 공식 OSCAL 콘텐츠로 표시하지 않는다.
- SSP는 실제 시스템 구성과 구현을, Assessment Plan은 검사 범위·방법을, Assessment Results는 관측·평가 결과·근거 참조를 표현한다. 선택한 OSCAL 버전의 필수 참조를 포함한 최소 문서 묶음을 검증한다.
- Git은 기준 문서와 변경 이력을 관리한다. Postgres는 평가 이력과 조회용 projection을 유지한다. GHCR·Rekor는 기존 서명·증거 저장 및 무결성 검증 역할을 유지한다. Manyfast 화면은 백엔드가 제공하는 OSCAL 연결 관계와 현재 판정을 표시한다.
- SBOM은 CycloneDX로 유지하며 OSCAL에서 digest·해시와 함께 참조한다. OSCAL 채택으로 SBOM 형식이나 서명 검증을 대체하지 않는다.
- 기존 5값 상태·TTL·승인·복구 규칙은 프로젝트 정책이다. OSCAL 표준 상태와 일대일 대응한다고 가정하지 않으며 명시적 매핑과 필요한 namespaced 확장 속성으로 손실 없이 보존한다. 구체적인 매핑·확장 namespace·버전은 실험에서 정한다.
- 과거 Assessment Results는 평가 당시 결과로 보존한다. 현재 증거 만료에 따른 판정과 과거 결과를 구분하고, 새 평가에는 기준 문서·정책 버전 및 평가 시각을 연결한다.
- 이미지 검증 요구사항 하나를 Catalog/Profile → 구현 설명·평가 계획 → Kyverno 검사 → Assessment Results → 조회 API·화면으로 연결하는 최소 실험을 추가한다. 한 세부 검사의 성공을 DEPLOY-REQ-4 전체 충족으로 확대하지 않는다.
- C2P 공식 저장소에서 Kyverno 정책 생성과 PolicyReport의 Assessment Results 변환 예제를 확인했다. 프로젝트 정책·선택한 버전에서 실제 동작하는지는 미검증이다. OSCAL 자유 서술을 임의 Kyverno 정책으로 자동 변환할 수 있다고 가정하지 않는다.

## 증거 유효기간

아래 값은 프로젝트 초기 정책이며 설정 파일에서 관리한다.

| 증거 | 수집·재검사 주기 | 유효기간 |
|---|---|---|
| ArgoCD 상태 | 1분 | 5분 |
| Scorecard | 하루 | 48시간 |
| 이미지 취약점 검사·VSA | 하루 | 48시간 |
| 빌드 서명·provenance | 해당 digest 기준 검증 | 시간만으로 만료시키지 않고 서명자 신뢰·정책 변경 시 재평가 |
| SBOM | 이미지 digest·소스 커밋에 연결 | 시간만으로 만료시키지 않으며 품질·신뢰 검증을 수행 |

승인 발행 직전에 필수 증거의 유효성을 다시 확인한다. **증거 스냅샷의 유효기간**과 **배포 실행 lease**는 별도 필드로 보존한다. `evidenceFreshUntil`은 발행 시각(`issuedAt`)보다 뒤여야 하며, 이것으로 승인 발행의 근거가 유효했음을 증명한다. `executionLeaseExpiresAt`은 발행 뒤 최대 10분으로 고정하고 CI 계약과 admission이 모두 이 상한을 확인한다. 따라서 5분 ArgoCD 상태 증거가 lease 도중 만료되더라도, 동일 commit·렌더링 명세 hash·이미지 digest·정책 버전으로 묶인 Pod의 지연 생성·재시작은 lease 안에서 계속할 수 있다. lease 연장은 새 승인 발행이며, 대상의 어느 값이라도 바뀌면 재평가한다.

이 분리는 증거 만료를 무시한다는 뜻이 아니다. CI는 발행 때 모든 필수 증거를 확인하고, admission은 별도 갱신되는 `trustState=trusted`와 `trustStateExpiresAt`(최대 1분 신선도)을 확인한다. 정책 변경, 서명자 신뢰 철회, 차단 취약점, 신뢰 상태 갱신 실패는 execution lease 중에도 즉시 거절한다. 기존 승인으로 허용되는 범위는 아래의 동일 설정 장애 복구 예외에 한정한다.

## 배포·복구·GitOps

- 만료 증거는 새 배포를 차단하고 알럿을 발생시킨다. 실행 중인 서비스는 증거 만료만으로 종료하지 않는다. 실제 침해 격리는 별도 런북으로 정의한다.
- 증거 만료만 발생했고 현재 신뢰 상태가 유효하면 기존 승인 digest·배포 설정으로 장애 복구를 허용하고 예외 사용을 기록·알림한다. 신뢰 철회, 차단 대상 취약점 확인, 정책 변경 후 재평가 미완료, 신뢰 상태 갱신 지연은 이 예외로 우회하지 못한다. 실제 admission 구현은 선행 실험 대상이다.
- Tilt는 별도 개발 namespace의 SSDF만 담당한다. 배포 검증 환경은 SSDF를 포함해 Argo가 관리한다. Git 관리 배포 명세 변경은 Argo에 한정하고 VSO·컨트롤러·설정 Job은 담당 리소스에 한정해 쓰기를 허용한다.
- 승인 대상은 Git 커밋, 렌더링된 배포 명세 해시, 이미지 digest 목록, 정책 버전이다. 어느 하나라도 바뀌면 재평가한다. 장애 복구 예외도 이 기록을 기준으로 판단한다.
- Secret 참조·Vault 역할·권한 설정은 승인 대상에 포함하며 비밀 값 자체는 제외한다. 동일 역할·권한 내 자격증명 교체는 운영 이벤트로 기록한다. Secret 참조·역할·권한 변경은 재승인이 필요하다.
- 정책 변경 시 유효한 기존 증거로 재평가하고 새 승인을 발행한다. 재평가 전에는 이전 승인으로 신규 배포·자동 복구를 허용하지 않는다. 실행 중인 Pod는 유지한다.
- 차단 대상 취약점 확인 시 기존 승인을 재평가해 신규 배포·자동 복구 예외를 차단한다. 실행 중인 Pod는 유지하며 알럿을 발생시킨다. 필요한 복구는 Git에 기록한 기한부 취약점 예외를 거쳐야 한다.
- 차단 판정·정책 변경을 기록한 시점부터 1분 이내에 admission에 반영한다. Admission이 확인하는 신뢰 상태가 1분 넘게 갱신되지 않으면 신규 배포와 복구 예외를 차단한다. 이 1분은 취약점 공개부터 탐지까지의 시간 목표가 아니며, 일일 재검사 주기와 구분한다.
- CLI 또는 수동 실행 CI에서 증거 재수집 → 재평가 → 승인 기록 생성을 지원한다. 차단 기준을 우회하지 않는다.
- 배포 승인 증거는 지정한 CI 워크플로만 발행한다. CLI는 워크플로를 호출하고 백엔드는 판정·조회만 한다. 수집기는 정제한 증거를 서명해 프로젝트 GHCR에 게시하며 CI가 서명·대상·신선도를 검증한 뒤 같은 판정 규칙으로 평가한다. 수집기·대시보드에는 배포 승인 서명 권한을 주지 않는다. 이 역할별 서명 identity와 검증 조건은 선행 실험에서 구현한다.
- 부트스트랩은 최소 구성요소 목록과 고정 digest에 한정한 설치·복구 예외다. 검증 체계가 준비되면 해당 이미지도 검사·VSA 발행을 완료한다. namespace 전체를 영구 면제하지 않는다.

## 배포 실행과 성공 판정

- 배포 전에는 현재 승인된 구성의 상태와 새 배포 대상을 검증한다. 새 커밋의 `Synced`·`Healthy`는 배포 후 확인하며, 승인된 전환 중의 차이와 무단 변경을 구분한다.
- 배포 후 검사 제한 시간의 초깃값은 10분이다. 모든 배포에서 ArgoCD `Synced`·`Healthy`, LN·DB 관련 배포에서는 실제 양방향 결제까지 확인한다. 초과하면 실패로 처리하고 실측에 따라 제한 시간을 조정한다.
- 배포 후 검사 실패 시 일반 후속 배포를 차단하고 알럿을 발생시킨다. 자동 롤백은 하지 않으며 원인 확인 후 Git revert 또는 복구 런북을 선택한다.
- 복구 배포는 실패한 배포를 명시적으로 참조하고 새 승인·서명·SBOM·취약점·정책 검사를 통과해야 한다. 이는 증거 만료 때 기존 승인으로 동일 설정 Pod를 재생성하는 장애 복구 예외와 다른 경로다.
- 배포 검증 환경에서는 한 번에 하나만 배포한다. 승인 직전에 대상 커밋을 다시 확인하고 배포 후 검사가 끝날 때까지 다음 배포를 대기시킨다. 실패 시 일반 배포 대기는 유지하고 승인된 복구 배포만 진행한다.

## SBOM과 재검사

- 모든 배포 이미지에 검증 가능한 SBOM을 필수 증거로 요구한다. 누락, 서명 실패, 대상 digest 불일치는 신규 배포를 차단한다. 기존 부트스트랩·장애 복구 예외 범위는 유지한다.
- Trivy로 CycloneDX JSON을 생성하고 cosign 서명 attestation으로 프로젝트 GHCR에 보관한다. 취약점 보고서와 VSA는 이미지 digest와 SBOM 해시를 참조한다. 도구 버전·저장 형식 간 호환성은 첫 선행 실험에서 검증한다.
- 이미지 SBOM은 digest에 연결한다. 자체 코드에는 소스·lockfile 기반 SBOM도 생성해 Git 커밋에 연결한다. 이미지와 소스의 분석 범위를 구분하고 업스트림 빌드 의존성은 확보한 증거 이상으로 주장하지 않는다.
- 품질 필수 검사는 형식 유효성, 대상 digest 연결, 생성 도구·버전, 분석 범위, 분석 오류 여부다. 소스 SBOM의 대상 연결은 Git 커밋으로 확인한다. 패키지 개수만으로 통과시키지 않으며 Go 바이너리 등 실제 구성요소 식별 여부를 표본 검증한다. 분석 실패·필수 범위 누락은 통과시키지 않고 미분석 영역은 화면에 명시한다.
- 저장한 SBOM을 최신 취약점 DB로 매일 재검사한다. 보고서에 SBOM 해시, 스캐너 버전, 취약점 DB 버전·발행 시각·갱신 시각을 기록한다. SBOM 자체에는 시간 만료를 적용하지 않으며 취약점 검사 결과에는 48시간 TTL을 적용한다.
- 검사 시작 시 취약점 DB 갱신을 시도한다. DB 발행 후 48시간을 넘으면 해당 검사를 승인 증거로 사용하지 않는다. 갱신 실패 시 48시간 이내의 캐시는 사용할 수 있으나 실패 사실을 기록한다. 검사 미완료는 `no_evidence`, 오래된 DB 사용은 신선도 검사 실패다.

## 공급망과 기록

- Scorecard는 lnd·aperture 소스 저장소를 평가한다. 이미지 검사·admission 검증은 initContainer·sidecar·인프라를 포함한 실제 배포 이미지 전체에 적용한다. aperture는 배포 전까지 배포 증거를 요구하지 않는다.
- 수정 버전이 있는 High·Critical 취약점과 수정 버전이 없는 Critical은 차단한다. 수정 버전이 없는 High는 경고다. 예외는 Git에 대상 digest·취약점 ID·사유·만료일을 기록하고 만료 후 다시 차단한다.
- VSA는 프로젝트용 GHCR OCI 저장소에 보관하고 원본 이미지 digest에 연결한다. 원본 이미지는 기존 레지스트리에서 받는다. 실제 패키지 경로·발행 identity·접근 권한·Kyverno 조회 호환성은 아직 미검증이다.
- 일일 해시체인 체크포인트 외에 배포 승인에 사용한 증거 묶음도 승인 전에 서명·Rekor 기록한다. 외부 기록 실패 시 새 승인을 보류하며 미기록 증거는 화면에서 구분한다. Rekor 기록은 수집된 내용의 진실성이나 원본 데이터 백업을 대신하지 않는다.
- Phase 6은 Audit와 격리 namespace의 실제 차단 테스트다. Phase 7에서 전체 이미지의 VSA·검증 경로를 준비한 뒤 Enforce로 전환한다.
- 전체 Phase 구현 전에 [네 선행 실험](preflight-experiments.md)을 검증한다.

## 남은 구현·검증 항목

- 서명 identity, GHCR 패키지 경로, 승인·VSA·증거 데이터 형식, 명세 정규화, SBOM 분석 범위별 fixture, DB 역할 권한 SQL은 선행 실험에서 구체화한다. 사용자 합의를 동작 검증으로 취급하지 않는다.
- 5분짜리 ArgoCD 증거를 쓰는 배포 승인과 최대 10분짜리 배포 후 검사 사이에서 지연 Pod 생성·재시작이 어떻게 처리되는지 실험 2에 포함한다. 발행 시 증거가 유효하고 10분 이내의 동일 대상 execution lease라면 허용하며, lease 만료·대상 변경·신뢰 상태 1분 초과는 거절하는 것을 실제 admission에서 검증해야 한다.
- C2P의 프로젝트별 호환성, remote signer, HA 구성은 미검증으로 유지한다.

## 근거와 검증 한계

- [NIST OSCAL 모델](https://pages.nist.gov/OSCAL/learn/concepts/layer/): 통제 정의·적용 범위·구현·평가 모델의 역할을 확인했다. 실제 적용 버전과 스키마 검증은 선행 실험에서 고정한다.
- [C2P 공식 저장소](https://github.com/oscal-compass/compliance-to-policy): Kyverno 정책 생성·결과 변환 예제의 존재를 확인했다. 실행 검증은 아직 하지 않았다.

- [Vault dev 모드 공식 문서](https://developer.hashicorp.com/vault/docs/concepts/dev-server): 메모리 저장소이므로 재시작 시 데이터가 사라진다. 언실러 영속화 결정의 근거다.
- [NIST SP 800-204D §3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-204D.pdf): 신뢰 소스 정책, SBOM, 재스캔, SCM 쓰기 통제, 독립 리뷰를 다룬다. 해당 절은 읽었으나 구현 완료를 뜻하지 않는다. 1인 프로젝트의 독립 리뷰 한계도 예외로 기록해야 한다.
